# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TeamClaude is a transparent HTTP proxy that sits between Claude Code and the Anthropic API, managing multiple Claude (Max/Pro/API-key) accounts and rotating between them when one nears its session (5h) or weekly (7d) quota. Published as `@karpeleslab/teamclaude`. The qjc fork adds a second, fully isolated **Codex mode** that pools ChatGPT OAuth accounts in front of the ChatGPT Codex backend (see "Codex mode" below), and a third, **Antigravity (agy) mode** that pools Google AI Pro/Ultra accounts in front of Cloud Code for the Antigravity CLI (see "Antigravity (agy) mode" below), and a fourth, **Grok mode** that pools xAI SuperGrok accounts in front of grok's CLI chat proxy for the Grok Build CLI and other local clients (see "Grok mode" below), and a fifth, **Cursor mode** that pools Cursor accounts in front of Cursor's API and agent backends for the Cursor CLI `cursor-agent` (see "Cursor mode" below).

## Commands

There is **no build step**. Development is run directly against source.

```bash
node src/index.js <command>        # run any CLI command locally (server is the default)
node src/index.js stop             # stop the running server (restart = stop + start)
npm start                          # = node src/index.js (starts the proxy server)
npm test                           # = node --test  (tests live in test/)
npm run lint                       # = eslint . (flat config in eslint.config.js)

# Use a throwaway config instead of ~/.config/teamclaude.json:
TEAMCLAUDE_CONFIG=./config.json node src/index.js server

# Codex (ChatGPT) pool — separate config ~/.config/teamcodex.json, default port 3457:
node src/index.js codex server     # every subcommand works with the `codex` prefix

# Antigravity (agy) pool — separate config ~/.config/teamagy.json, default port 3458:
node src/index.js agy server       # server/stop/restart/status/accounts/remove/reload/enable/disable/priority/env/import/login/run

# Grok (xAI SuperGrok) pool — separate config ~/.config/teamgrok.json, default port 3459:
node src/index.js grok server      # same command set as agy; login = xAI device-code flow

# Cursor (cursor-agent) pool — separate config ~/.config/teamcursor.json, default port 3460:
node src/index.js cursor server    # same command set as grok; login = Cursor browser flow (poll)
```

Under a teamclaude-supervised session (`TEAMCLAUDE_SESSION_SUPERVISED=1` is inherited) `run-env`/`run-recovery` tests fail; run the suite as `env -u TEAMCLAUDE_SESSION_SUPERVISED -u TEAMCLAUDE_HUD -u TMUX -u TMUX_PANE npm test`.

`config.json` is gitignored; `config.example.json` is the template. To exercise the proxy end-to-end, start `server` in one terminal and `node src/index.js run` (or `eval $(node src/index.js env)` then `claude`) in another.

## Hard constraints (do not break these)

- **Zero runtime dependencies.** This is an advertised feature — use only Node.js built-in modules. Do not add anything to `dependencies`.
- **ES modules, Node 18+.** `"type": "module"`, top-level `await` is used in `src/index.js`.
- **ESLint globals are explicitly enumerated** in `eslint.config.js`. If you use a new global (a timer, a Web API like `crypto`/`TextEncoder`), add it to the `globals` map or `no-undef` will error.

## Architecture

Single CLI binary (`src/index.js`) dispatches subcommands; `server` boots the proxy. The main source files keep clear ownership:

- **`src/index.js`** — CLI dispatcher + all non-server commands (`stop`, `restart`, `import`, `login`, `env`, `status`, `accounts`, `remove`, `api`). Owns the **config-sync wiring** between the running server, the TUI, and external CLI invocations (see below), and the **server lifecycle**: a stable parent HTTP listener buffers requests and forwards them to a replaceable proxy worker, while `findRunningServer`/`stopRunningServer` discover and stop the parent via state file + port probe + `lsof`. `teamclaude run` auto-starts this supervisor when absent.
- **`src/server.js`** — the HTTP proxy and the request-forwarding loop (`forwardRequest`), including account acquisition (concurrency slot), retry, rate-limit handling, SSE streaming, and optional request logging.
- **`src/sse.js`** — SSE resilience helpers shared by the worker and the supervisor relay: `SseFramer` (forward only whole SSE events; track whether a terminal event was delivered) and `sseErrorEvent` (the synthetic retryable `overloaded_error` frame injected on an abnormal mid-stream end — see "Mid-stream SSE recovery" below). No proxy state.
- **`src/account-manager.js`** — `AccountManager` class: in-memory account state, use-or-lose selection, **per-account concurrency cap + overflow queue** (`acquireAccount`/`releaseAccount`), quota tracking from response headers, and token-refresh coalescing. The single source of truth for *live* credentials while the server runs.
- **`src/oauth.js`** — OAuth PKCE login, token refresh, profile fetch, and credential import from Claude Code. No proxy state here — pure functions.
- **`src/reauth.js`** — fail-closed account reauthentication: select one existing Anthropic OAuth account, verify the returned profile against its UUID (or legacy email), then replace only that account's credentials through the caller's atomic config writer.
- **`src/config.js`** — load/save of `~/.config/teamclaude.json` (override via `TEAMCLAUDE_CONFIG`, or `$XDG_CONFIG_HOME`; `TEAMCLAUDE_PROVIDER=codex` switches the default file to `~/.config/teamcodex.json`, `TEAMCLAUDE_PROVIDER=agy` to `~/.config/teamagy.json`, `TEAMCLAUDE_PROVIDER=grok` to `~/.config/teamgrok.json`, `TEAMCLAUDE_PROVIDER=cursor` to `~/.config/teamcursor.json`). Written `0o600`.
- **`src/codex.js`** — Codex-mode helpers, no proxy state: parse/import ChatGPT OAuth credentials (`~/.codex/auth.json` shape), token refresh against `auth.openai.com`, and `buildCodexProxyArgs` (the `-c model_provider` overrides that point the Codex CLI at the proxy).
- **`src/agy.js`** — Antigravity-mode helpers, no proxy state: agy login parsing (keychain `go-keyring-base64:` value or plain JSON, id_token identity), OAuth client resolution (config override → binary candidates verified by a token-endpoint probe), Google OAuth refresh/login, `loadCodeAssist`, quota-summary parsing, model → quota group, 429 classification, project rewrite, session affinity key, `agy run` binary/env.
- **`src/grok.js`** — Grok-mode helpers, no proxy state: xAI device-code login, refresh (public client, no secret), `~/.grok/auth.json` parsing, `/v1/user` lookup, inference-path test, session affinity key, `x-ratelimit` meter, identity-header rewrite, `grok run` binary/env.
- **`src/cursor.js`** — Cursor-mode helpers, no proxy state: browser login (PKCE + `/auth/poll`), session-JWT credentials, keychain/`auth.json` import (read only), Connect-JSON `GetMe`/usage calls, Connect frame peek + failure classes, chat affinity key, `cursor run` binary/env, and `h2cSniffer` (public-port h2c → worker tunnel).
- **`src/subscription.js`** — pure Codex cancellation metadata validation, exact account targeting, local-date conversion, and credential-free status snapshots.
- **`src/codex-session.js`** — exact Codex resume boundary: validates UUID session IDs and reads only the current surface's public `cmux surface resume get --json` binding. It fails closed instead of guessing from recent sessions or private state.
- **`src/system-metrics.js`** — host CPU/RAM/loadavg sampler; `GET /teamclaude/status` rides a `host` object along so `teamclaude status` and the TUI header can show the proxy machine's load.
- **`src/update.js`** — `<pool> update [--all]`: replaces a pool install's `src/`+`package.json` with a fork commit (git archive), refusing installs whose files are not in the fork's history, then (per-install `.update.lock`) waits for `x-teamcodex-active-requests` 0 twice and engages the deployment drain, swaps a pre-copied `src.new-*` in with two renames (records `.teamproxy-commit`), restarts only under a supervisor (systemd user unit, or on macOS a launchd job owning the `<pool>` tmux session), verifies (`status --json`, accounts, model list) and restores the backup on failure. Skips `teamproxy-app` (app-mode) installs and git checkouts. Spawns other processes only; no proxy state.
- **`src/tui.js`** — full-screen terminal dashboard (alternate screen buffer). Only used when both stdin and stdout are TTYs; otherwise the server logs plainly.

### Codex mode (qjc fork)

`teamclaude codex <cmd>` (or config `provider: "codex"`) runs a second, fully isolated pool for **ChatGPT OAuth accounts** in front of `https://chatgpt.com/backend-api/codex` — own config (`~/.config/teamcodex.json`, default port 3457), own quota/server-state files, zero overlap with the Claude pool. Key differences from Anthropic mode:

- **Accounts are ChatGPT OAuth only.** `codex login` runs the Codex CLI login inside a throwaway `CODEX_HOME` and imports the resulting `auth.json`; `codex import` reads an existing `~/.codex/auth.json`. Refresh routes by `account.provider` to `refreshCodexAccessToken` (auth.openai.com, Codex client id).
- **Codex CLI spawns resolve the real binary** (`resolveCodexCliBin` in codex.js, used by both `codex login` and `codex run`): `TEAMCODEX_CODEX_BIN` env override → the `codex` co-installed with the running Node (`dirname(process.execPath)/codex`) → bare `codex` PATH lookup. Rationale: a shell wrapper/symlink shadowing `codex` in PATH (e.g. a remote agent router) must not hijack `login`, whose throwaway `CODEX_HOME` has to be written on this machine (2026-08-04 incident). On win32 the sibling probe is skipped (the extension-less file next to `node.exe` is npm's unspawnable POSIX shim; the bare lookup resolves `codex.exe`). Tests stub the CLI via `TEAMCODEX_CODEX_BIN`, not a PATH shim. Spawn-ENOENT errors name the resolved path (`codexCliNotFoundMessage`).
- **Auth headers**: requests are forwarded with the account's `Bearer` token plus `chatgpt-account-id` (client-sent `authorization`/`chatgpt-account-id` are stripped first). Because the proxy injects pool credentials, `buildCodexProxyArgs` sets `requires_openai_auth = false`: the client Codex CLI needs no local ChatGPT login to run through the proxy, so a revoked/expired `~/.codex/auth.json` cannot surface the Codex sign-in screen while the pool is healthy (2026-08-03 incident; previously `true`).
- **Quota**: `x-codex-primary/secondary-used-percent` (+ `-reset-at`, `x-codex-rate-limit-reached-type`) are normalized into the same unified 5h/7d model in `updateQuota`, so selection, `switchThreshold`, throttling, and the TUI all work unchanged. Authoritative usage comes from per-account `GET /wham/usage` polls (startup + every `warmupIntervalMs`, plus an active per-account refresh right after a forwarded request completes when the data is older than `codexUsageActiveMs`, default 60s; freshness stamp `codexUsageAt` in status).
- **`codex run`** launches the Codex CLI with `buildCodexProxyArgs` overrides (`model_provider` base_url → the proxy) — analogous to `run` keeping Claude Code in subscription mode.
- **Cancelled subscriptions stay routable until evidence says otherwise.** `codex subscription cancel|clear` stores operator-declared metadata; `plan_type`, WHAM failure, 429, and generic 403 never prove termination. A terminal auth failure becomes `subscription-ended` only after a known end date or when the end date is unknown, and a completed Codex usage/inference response reverses that inference.
- **Automatic termination detection (no declaration needed).** The wham/usage poll doubles as a credential health check: `codexAuthFailureThreshold` (default 3) 401/403 poll failures accumulated without an intervening success escalate to one forced refresh + one confirm re-poll, and only agreement parks the account (existing `errorReason` values, in-memory cause tag `_errorFromUsagePoll`). A later valid usage poll auto-heals accounts parked by this watchdog (and `subscription-ended` ones); request-path 401 parks keep their stricter healing — attribution is exact: the watchdog tags a refresh-caused park only when `_errorFromRefresh` is true and tags its own confirm-path park synchronously with `markAuthenticationError`, so a request-path park landing during an awaited refresh/re-poll is never claimed (and never becomes poll-healable). 5xx/429/network noise neither counts nor resets, and any positive auth evidence (a valid poll or a completed inference via `markAccountSuccess`) resets the streak, so an actively-serving account is never quarantined by usage-endpoint-only 401/403s; `updateAccountTokens` (re-import) also clears the streak. **Circuit breaker:** a confirm-path park that would leave zero available accounts (`hasOtherAvailableAccount`, aligned with `_isAvailable`) is withheld — the streak stays consumed and the next threshold re-judges — so a usage-endpoint-only outage (WAF/contract change) can never empty an idle pool; request-path 401 parks and terminal refresh failures are deliberately not breaker-gated (real evidence may park the last account). Spec: `docs/specs/2026-09-01-codex-auto-subscription-detection.md`; tests: `test/server-codex-auto-detect.test.js`.
- **Unsupported Codex models fail closed.** Only the exact ChatGPT OAuth `400` contract creates a bounded account/model TTL quarantine; the rejected original POST is never replayed. A later continuation uses a configured fallback only before upstream dispatch when every eligible OAuth account is quarantined, and a chain dead-end returns an immediate `429` using the earliest TTL. Spec: `docs/specs/2026-08-31-codex-chatgpt-model-compatibility.md`; tests: `test/server-codex-model-compatibility.test.js`.
- **`codex resume [SESSION_ID]`** routes the exact ID through a final, non-overridable provider override. Without an ID it consumes the current cmux surface's trusted Codex checkpoint without passing direct Codex credentials to cmux, never the bounded recent-session picker. Remote/local execution flags are rejected because they bypass provider selection entirely.
- **Fleet-wide usage-limit fail-fast + Codex-native 429 body** (`docs/specs/2026-09-04-codex-usage-limit-fail-fast.md`): in continuity deadline mode the "No eligible capacity" loop no longer sleeps out the budget when the fleet is blocked by a KNOWN quota reset/throttle that lies beyond the remaining `continuityMaxWaitMs` (e.g. every account spent its weekly window, reset days away) — it breaks at once and finalizes as the deadline would (saved upstream 429 replay still wins). This part is provider-agnostic; the 60s quota-healthy fallback and the concurrency-capped case never fail fast. Then, for `provider: 'codex'` only, a quota dead end answers `429 {"error":{"type":"usage_limit_reached","message":…,"plan_type":"pro","resets_at":<unix seconds>}}` — the shape the Codex CLI renders natively as "You've hit your usage limit … try again at <time>" (verified against `codex-rs/codex-api/src/api_bridge.rs`) instead of the opaque "exceeded retry limit, last status: 429". `plan_type` comes from the pooled accounts' `planType` (soonest-recovering account, else most common; omitted when unknown or not a spelling the CLI accepts). `retry-after` is kept; Anthropic mode, the capped case, the 401 all-auth-failed path, and legacy `continuityMaxWaitMs: 0` polling keep their existing bodies. Tests: `test/server-codex-usage-limit.test.js`.
- **Automatic rate-limit reset credits** (`docs/specs/2026-09-05-codex-reset-credits.md`, `src/codex-reset-credits.js`): ChatGPT grants free "Full reset" credits (the Codex CLI's `/usage` picker); the proxy owns the accounts, so it redeems them. Each `wham/usage` poll folds `rate_limit_reset_credits.available_count` into `quota.codexResetCredits`. With `codexResetCredits: true`, policy `fleet` (default) redeems one credit on the best-stocked exhausted account at the acquisition dead end (BEFORE model fallback / fail-fast) and re-acquires; policy `account` also redeems on the account that just got an exhaustion 429 and retries it in place. `POST /wham/rate-limit-reset-credits/consume` `{redeem_request_id}` → `{code: reset|nothing_to_reset|no_credit|already_redeemed, windows_reset}`; a `reset` zeroes the local 5h/7d meters, lifts a throttle, decrements the cached count, and schedules an authoritative usage refresh 1.5 s later. Guards (both policies): single-flight per account, `codexResetCreditsCooldownMs` after ANY attempt, `codexResetCreditsReserve`, credit count must be known, only proxy-exhausted accounts, never a model-quarantined account (`canServe`), **one redemption pass per request** — charged by any walk that actually reached the backend or any spend-capable account-policy attempt; a walk with no eligible candidate leaves it unspent — (a reset the backend does not honour then fails fast instead of walking the pool), the walk stops after any outcome that may have spent a credit (`reset` with `windows_reset: 0`, timeout/network/5xx = indeterminate), and the account policy retries an account at most once per request without counting toward `maxRetries` (so a second 429 still ends in the Codex-native body). Three consistency fences: a response to a request dispatched BEFORE `quota.codexResetCreditResetAt` neither folds its `x-codex-*` meter nor throttles on 429 (it is retried); for `CODEX_RESET_CREDIT_GRACE_MS` (2 min) after a reset an authoritative `wham/usage` payload may not RAISE the meter; and inside that grace an accepted (non-429) response's `x-codex-*` meter is not folded either (the request is still counted). A genuinely failed reset still throttles via a real post-reset 429, which is always folded. The ledger is durable: `hooks.onResetCreditLedger` (wired to the quota snapshot writer in `src/index.js`) persists a `pending` cooldown stamp BEFORE the consume POST and the outcome right after, so a crash between the backend consuming a credit and the 60 s periodic snapshot cannot make a restart redeem the same account again. The exhaustion-429 retry backstop yields one extra recursion while a request's redemption pass is unspent (it shares `retryCount` with 5xx/auth failovers). Operator trigger `POST /teamclaude/codex/reset-credit?account=<name>` (loopback + proxy API key, body-free, mirrors `/teamclaude/rotate`; the supervisor in `src/index.js` fences it because the worker only ever sees loopback) bypasses policy/cooldown/reserve. Status carries `resetCredits: {enabled, policy, cooldownMs, reserve}`; a dead end with no eligible candidate logs one throttled `[TeamCodex] Reset credit: no eligible account (...)` line with per-account reasons. Off by default; Anthropic mode ignores it. Tests: `test/codex-reset-credits.test.js`, `test/codex-reset-credits-outcomes.test.js`, `test/server-codex-reset-credits.test.js`, `test/server-codex-reset-credits-guards.test.js`, supervisor fence in `test/server-supervisor.test.js`.
- **`activeWarmup` defaults off** in codex mode (no capture-and-replay probe shape for the Codex backend); the `/v1/oauth/token` relay is Anthropic-mode only.
- Ops note: like Anthropic mode, a running server does **not** see accounts added later via CLI — reload via TUI `R` or restart (`syncAccountsFromDisk`); a headless daemon needs the restart path.

### Antigravity (agy) mode (qjc fork)

`node src/index.js agy <cmd>` (or an inherited `TEAMCLAUDE_PROVIDER=agy`) runs a third, fully isolated pool of **Google AI Pro/Ultra accounts** used by the Antigravity CLI, in front of `https://daily-cloudcode-pa.googleapis.com` (`agyUpstream`) — own config (`~/.config/teamagy.json`, default port 3458), own quota/server-state files. Facts, measurements, and the decisions below: `docs/specs/2026-10-10-agy-mode.md`.

- **Mode and config must agree.** agy mode is the `agy` prefix or the env (`AGY_MODE` in index.js; help and the unsupported-command refusal key on it too). Before any command runs, index.js refuses an agy mode reading an existing config whose `provider` is not `"agy"` — **including no provider key**, which is what a real Claude config looks like — and a Claude/Codex mode reading a `provider: "agy"` config (`agyConfigMismatch`; Claude ⇄ Codex keeps its old behavior). Only a missing file is created, as an agy config. The agy config writers (`assertAgyConfig` in `upsertAgyAccount` and the OAuth-client cache) and the worker's live reloads refuse anything but `provider: "agy"` too. Recommend the `teamagy` wrapper (`TEAMCLAUDE_PROVIDER=agy`, `TEAMCLAUDE_CONFIG=~/.config/teamagy.json`, `index.js agy "$@"`); never `teamclaude agy …` through a wrapper that pins the Claude config. The supervisor forks the worker, and `agy run` auto-starts the server, with the `agy` prefix so an entry point that clears `TEAMCLAUDE_PROVIDER` (`src/teamclaude.js`) cannot drop the mode.

- **agy stays the client.** `agy run` auto-starts the server (`ensureProxyRunning`) and spawns agy with `CLOUD_CODE_URL=http://127.0.0.1:<port>`; agy keeps its own login, settings and MCP, so **agy must be signed in locally once** (a login-free ADC run reaches the proxy but agy then refuses to list models). The proxy strips `authorization`, `x-api-key`, `x-goog-api-key`, `x-goog-user-project`, injects the pool account's `Bearer`, keeps the user-agent, and forwards any `/v1internal…` path generically (never an allow-list). The child env drops `TEAMCLAUDE_PROVIDER`/`TEAMCLAUDE_CONFIG` so tools agy spawns are not pointed at this pool. Binary: `TEAMAGY_AGY_BIN` → `agy` next to node → `~/.local/bin/agy` → PATH.
- **Accounts.** `agy import` reads agy's keychain login (macOS `security`, service `gemini` / account `antigravity`; `--file` for the same JSON elsewhere); `agy login` runs a Google installed-app OAuth (PKCE, `127.0.0.1` loopback, offline + consent) for further accounts without touching agy's own login. Identity is the id_token `sub` (re-import updates in place). Both call `loadCodeAssist` once and store `tierId` (paid tier first) and `projectId`; no paid tier warns. Refresh tokens are never revoked (the local agy login may be the same account).
- **OAuth client is never in the repo** (public, push protection). Config `agyOAuthClientId`/`agyOAuthClientSecret` win; otherwise the id_token `aud` plus a byte scan of the agy binary (the `1071006060591-` id, every `GOCSPX-` + 28 secret-alphabet bytes, including the head of a longer run — Go strings are glued, and agy 1.3.3's right secret is exactly such a head while a free-standing one belongs to another client). The bytes cannot decide, so each candidate pair is **probed**: a refresh with a bogus token answers `400 invalid_grant` for the right client and `401 invalid_client` for a wrong one (no side effect). Exactly one accepted pair is cached into the 0600 config by import/login/server start; none, several, or an unclear answer is an error asking for the config values. Refresh routes by `account.provider === 'agy'` to `_refreshAgy` (`refreshAgyAccessToken`, `accountManager.agyOAuth`): `invalid_grant` is the terminal verdict → existing `refresh-failed` park; `invalid_client` is the client's fault — re-resolve once (`agyOAuthRecover`, coalesced, 5-min pause after a failure) and retry; if still refused only that refresh fails (a lapsed token becomes a healable `refresh-failed`, never `auth-revoked`).
- **Project rewrite.** When the selected account has a `projectId` and the body's top-level string `project` differs, it is rewritten (per attempt, so failover re-targets; `content-length` resynced); otherwise the body is byte-identical. Consumer accounts all share `aicode-consumers`, so this is normally a no-op.
- **Quota = two groups.** No quota headers exist; `retrieveUserQuotaSummary` per enabled, un-parked account at startup, every `warmupIntervalMs` (agy default 10 min), after a completed inference when older than `agyUsageActiveMs` (default 2 min), and right after an exhaustion 429 (queued behind an in-flight refresh, never dropped) — with the latest client user-agent. Token totals come from the final frame's `usageMetadata.totalTokenCount` (`agyUsageFromResponse`). `quota.agyGroups.{gemini,3p}` hold 5h/weekly utilization + `blockedUntil`; `gemini` mirrors into `unified5h/7d` (status headline, TUI Ses/Wk; the TUI third bar and `status` show `3p`). A request's group is its `model` (`claude-*`/`gpt-*` → `3p`, else `gemini`); `_isNearQuota` for an agy account checks only that group, and a **model-less call is never gated** (agy must always read tier/quota). A missing `remainingFraction` is unknown in a routine summary but exhausted right after a 429.
- **429.** Inference path (`streamGenerateContent`/`generateContent`) + non-capacity reason → block (account, group) (`RetryInfo` or 5 min, then the summary's exhausted bucket reset), fail over at once; the other group stays routable. `MODEL_CAPACITY_*`, a model-less call, or any other path → no account state, `rateLimitFailovers` alternates, then pass-through. No account left → the upstream 429 body unchanged; with none from this request, a Google RPC shaped 429 whose `retry-after`/`RetryInfo` is the soonest group recovery. Proxy-made 401s (every account failed auth) are Google RPC shaped as well. Continuity and stream recovery are off (SSE bytes untouched; the supervisor relay does not frame agy either).
- **Stickiness** (agy keeps server-side state per account): `reevalIntervalMs` defaults to 0, agy accounts are always "measured" (no warm-up hopping), affinity is keyed by trajectory id (ACL write ↔ `requestId` 4th segment) else `request.sessionId` else socket, and new configs default `maxConcurrentPerAccount` to 8. The account changes only when it cannot serve the request's group.
- **Not offered:** reauth, subscription, api, reset credits, resume, cmux, BYOK-specific paths, Gemini CLI / API-key / Vertex, login-free ADC. Remote clients still need the proxy key at the supervisor, which agy cannot send — effectively loopback-only. Tests: `test/agy*.test.js`, `test/server-agy.test.js`.

### Grok mode (qjc fork, 2026-10-15)

`node src/index.js grok <cmd>` (or an inherited `TEAMCLAUDE_PROVIDER=grok`) runs a fourth, fully isolated pool of **xAI SuperGrok accounts** in front of `https://cli-chat-proxy.grok.com` (`grokUpstream`) — own config (`~/.config/teamgrok.json`, default port 3459), own quota/server-state files. Facts, measurements and the decisions below: `docs/specs/2026-10-15-grok-mode.md`.

- **Mode and config must agree** exactly like agy (`poolConfigMismatch` in index.js covers both dedicated pools; the agy rules and messages are unchanged). Wrapper: `teamgrok` = `TEAMCLAUDE_PROVIDER=grok TEAMCLAUDE_CONFIG=~/.config/teamgrok.json node src/index.js grok "$@"`. The supervisor forks the worker and `grok run` auto-starts the server with the `grok` prefix.
- **grok stays the client.** `grok run` spawns grok with `GROK_CLI_CHAT_PROXY_BASE_URL=http://127.0.0.1:<port>/v1` (pool selectors dropped from the child env); grok must be signed in locally once. Binary: `TEAMGROK_GROK_BIN` → `$GROK_HOME/bin/grok` (`~/.grok/bin/grok`) → `~/.local/bin/grok` → PATH. Every path is forwarded generically; bodies are byte-identical (zstd request bodies included), SSE untouched.
- **Headers.** Client `authorization`, `x-api-key`, `cookie` dropped, pool `Bearer` injected. Identity headers the request carries (`x-userid`, `x-grok-user-id`, `x-email`, `x-teamid`) are rewritten per attempt to the account's `accountUuid`/`email`/`teamId` (dropped when the account has no value; never added). A missing `x-grok-client-version` is filled with the last value seen from a `grok-shell/` user-agent, else `grokClientVersion`, else `1.0.46` (upstream answers 426 without it).
- **Accounts.** `grok login` = OAuth device flow against `auth.x.ai` with grok's public client id (`grokOAuthClientId` overrides; test hooks `grokTokenUrl`, `grokDeviceUrl`); `--json` emits `auth_url` with `user_code` + `browser_opened:false`. `grok import` reads `~/.grok/auth.json` (`--file`) and warns about the shared refresh token. ### Request flow (`forwardRequest` in server.js)

0. The supervisor in `src/index.js` owns the public port and buffers each request under the same admission/body bounds before forwarding it to the worker's loopback-only listener. If that worker dies before response headers, the request waits for the replacement worker and is retried (bounded); the public listener never disappears. If the worker dies MID-response: an SSE relay (with `streamRecovery` on) is framed to whole events, so the supervisor ends the client's response with the synthetic retryable `overloaded_error` event (see "Mid-stream SSE recovery" below) and the client's own retry lands on the replacement worker; a non-SSE mid-response death still destroys the client socket (partial JSON is not salvageable).
1. localhost clients skip proxy-API-key auth (`isLocal` check); remote clients must send the matching `x-api-key`.
2. `GET /teamclaude/status` returns a credential-free, identity-redacted status snapshot. Account display names and stable IDs are returned only to a localhost caller that supplies the configured proxy API key and `x-teamcodex-status-identity: 1`.
3. **`POST /v1/oauth/token` is relayed untouched** (`relayRaw`) — the client manages its own token lifecycle independently of the proxy's. Never intercept or rewrite it; doing so causes token-rotation conflicts.
4. Body is fully buffered (needed to replay on 429 retry). Hop-by-hop headers, `x-api-key`, and `accept-encoding` are stripped before forwarding (Node `fetch` auto-decompresses, so `content-encoding`/`content-length` are also dropped on the way back).
5. Account acquired via `acquireAccount()` (reserves one of the account's concurrency slots — see Concurrency below); OAuth token refreshed if expiring within 5 min. The slot is released in the request's `finally`; a failover (429/5xx/error) releases the current slot via `releaseHeld()` before recursing onto another account, while a 401 same-account refresh-retry keeps the slot (`ctx.heldIndex`).
6. **429 handling classifies the 429 (`isExhausted`, checked after `updateQuota` folds in the response headers) before acting**:
   - **Account-quota exhaustion** (`anthropic-ratelimit-unified-status: rejected`, or measured utilization ≥ threshold): throttle the account for `retry-after` (clamped to `[1s, 5m]`) and immediately re-dispatch to another available account. When *every* account is throttled, `getActiveAccount` returns `null` and the client gets a `429` to back off itself. This keeps cold-start warm-up fast (an exhausted account is skipped in one round-trip, not a 60s stall).
   - **Non-exhaustion 429**: try only `rateLimitFailovers` alternate accounts, then open a shared cooldown and retry internally when continuity mode is enabled. The account is not poisoned and a request-global limit is not amplified across the fleet.

   When the active account crosses `switchThreshold`, the *next* request switches to the highest-priority account (see Account selection below).
6.5. **401 handling is cascade-guarded** (`AUTH_401_CASCADE_THRESHOLD`, qjc fork): a 401 that survives the forced token refresh parks its account as `error`/`auth-revoked` via `markAuthenticationError` — but only while the 401 is plausibly about the credential. `ctx.auth401` records the accounts whose 401 was **unexplained** (they were not already parked); once a second distinct account rejects the SAME request, the shared variable is the request, not the credentials, so the proxy rolls back the park this request performed and parks nobody else for it. Rollback is gated by a park-ownership stamp (`_authParkSeq`) plus the observable state, deliberately NOT by the credential generation (the background refresh sweep bumps that while leaving an `auth-revoked` park in place, which would strand a just-refreshed account). `ctx.auth401` joins the per-request exclusion set, and both fleet-wide "everyone failed auth" checks count it, so a request nobody authenticates still surfaces its 401 promptly instead of sitting out the continuity deadline. Accounts already parked by their own evidence (a failed refresh) are neither counted, relabeled, nor revived. Rationale + the outage that motivated it: `docs/specs/2026-09-05-auth-401-cascade-guard.md`; tests: `test/server-401.test.js`.
7. **Transient network errors** (`ECONNRESET`/`ETIMEDOUT`/`fetch failed`/undici `terminated` with a socket-error `cause`): before any response bytes went out, the request fails over to another account like a 5xx (per-request `tried5xx` exclusion; the account is NOT marked `'error'` — a network blip is not a bad credential). Non-SSE responses are buffered BEFORE headers go out, so a mid-body death on them stays on this retryable pre-headers path. Mid-stream SSE (headers sent, events delivered — not replayable) is handled by **Mid-stream SSE recovery** below: the proxy ends the response with a synthetic retryable error event instead of `res.destroy()`; the destroy remains only for the codex/opt-out legacy path and for a non-SSE response whose headers somehow already went out. This is a qjc-fork design choice, not a bug fix: current upstream classifies the same errors as transient and destroys deliberately, reasoning that Node's fetch connection pool is process-wide so another account would reuse the same poisoned pool. In practice that surfaced as "Response stalled mid-stream" in Claude Code, so this fork retries on a different account while nothing has been sent yet. Do not describe upstream as "destroying unconditionally" in docs or posts; it is verifiably not what upstream does (verified 2026-07-25 against upstream/master src/server.js).
8. All accounts unavailable → continuity mode waits for the computed reset and retries; legacy mode returns `429` with `retry-after`.

### Mid-stream SSE recovery (`streamRecovery`, qjc fork)

An SSE response that dies MID-stream (upstream network death, silent truncation without `message_stop`, or the worker being killed under the supervisor) used to reach Claude Code as a raw truncated stream — surfaced as **"API Error: Connection closed mid-response. The response above may be incomplete."**. Measured against the installed Claude Code bundle (2.1.220, 2026-07-26): Claude Code's own retry machinery only applies while **no non-thinking content block has streamed yet** — an in-stream `overloaded_error` in that window is retried (3 attempts, backoff, then model fallback; matched by the `"type":"overloaded_error"` substring even with no HTTP status), and a raw connection loss in that window takes the network-retry path (up to `CLAUDE_CODE_MAX_RETRIES`); once content HAS streamed, the turn finalizes as a partial response regardless. `config.streamRecovery` (default on; anthropic mode only — the Codex backend has a different in-stream error contract) maximizes what is recoverable at each stage:

- **Whole-event framing** (`SseFramer` in `src/sse.js`): both the worker's `streamResponse` and the supervisor's SSE relay forward only complete SSE frames (split on the blank-line boundary, LF or CRLF), so the client's SSE parser is never left holding half a JSON payload. Byte fidelity is preserved — flushed bytes are a contiguous prefix of the stream. A pathological frame beyond 4 MiB degrades to raw passthrough (memory bound wins).
- **Deferred headers → transparent replay**: in recovery mode the client's response headers are held until the first whole frame is ready. An upstream that dies BEFORE producing any frame therefore leaves the response untouched (`preStreamFailure`), and the whole request is replayed on another account with the client none the wiser; when no alternate remains, a real HTTP `529` + `overloaded_error` JSON is returned — the shape every client reliably auto-retries. Only a death AFTER events were forwarded needs the in-stream injection below.
- **Terminal tracking**: the framer records whether a terminal event (`message_stop` / `error`; `response.completed|failed|incomplete` / `[DONE]` for codex-shaped streams) was delivered. A stream that ends without one is a truncation even when the HTTP end was "clean".
- **Synthetic retryable error**: on an abnormal end the relay appends `event: error` with `{"type":"error","error":{"type":"overloaded_error",...}}` — the exact shape the Anthropic API uses for in-stream capacity errors — and ends the response cleanly. In the pre-content window (message_start / pings / thinking) Claude Code classifies it as retryable and re-issues the request by itself; the retry then benefits from normal account failover (and, after a worker crash, lands on the replacement worker). Once content has streamed, no client retries anything (verified in the 2.1.220 bundle) — the injection still wins on hygiene: the partial response finalizes cleanly at an event boundary (no half-frame JSON in the parser) and the session continues with the partial content, instead of a hard socket error. If a terminal event WAS already delivered, nothing is injected (a spurious error after `message_stop` would fail a completed message).
- **Usage side buffer is raw bytes** (`splitSseEvents`): the usage-parsing buffer in `streamResponse` splits events on the byte-level `\n\n` boundary, never on decoded text. Reservations are counted in raw bytes, so a text-based split desynchronises the ledger whenever an upstream chunk ends inside a multi-byte character (Korean output does this constantly) and throws `Auxiliary response buffer reservation underflow` — which, thrown from the `finally`, left client responses open forever (2026-09-08 incident). Any change here must keep `test/server-stream-usage-multibyte*.test.js` green and pass the deploy canary (`docs/runbooks/teamcodex-runtime-deployment.md`).
- **No account poisoning**: a mid-stream death mutates no account state — the response was partially delivered, so the only recovery that helps is the client retrying.
- Opt-out with `streamRecovery: false` restores the legacy raw passthrough + destroy behavior. Tests: `test/sse.test.js`, `test/server-midstream.test.js`, `test/supervisor-midstream.test.js`.

### BYOK compatibility surface (`config.byok`, qjc fork)

Third-party clients that support "bring your own key" (a base URL + an API key per provider — e.g. an AI browser) cannot reach this proxy on the normal paths. Upstream rejects them twice over: a request whose `system` lacks the Claude Code marker gets an opaque headerless 429, and a renderer-context request carrying `Origin` gets `400 Disallowed CORS origin`. A client cannot inject a system block from its provider config, so the proxy has to supply both — **on a dedicated path prefix only**.

- **Structural isolation, not a classifier.** BYOK traffic arrives on `<prefix>/v1/...` (default `/byok`), is canonicalized to `/v1/...`, and is marked `ctx.byok`. Claude Code arrives on `/v1/...` and therefore cannot enter the lane at all — its request bytes, and with them its prompt-cache keys, are provably untouched (`test/server-byok.test.js` asserts byte identity). Matching is segment-exact, so `/byokish/...` is not the surface.
- **Shape normalization** (`src/byok.js`, pure functions): the marker block is prepended to `system` only when absent (string and array forms; client content preserved after it), `content-length` is resynced because it is forwarded verbatim, and `origin`/`referer`/`sec-fetch-*` are dropped before dispatch. `OPTIONS` is answered locally — relaying a preflight upstream fails. An unparseable or non-object body is forwarded unchanged.
- **Own credential, and know the network boundary.** The surface requires `byok.apiKey` and does **not** inherit the localhost auth bypass (any local process can reach the port). The worker also refuses a non-loopback peer with 403, but know what that is worth: the supervisor owns the public port and re-dials the worker over loopback (`index.js`), so the worker's check **never fires in the shipped topology**. Remote traffic is gated by the supervisor's `proxy.apiKey` check instead, and the two checks are independent per-header matches (`x-api-key` vs `Authorization: Bearer`) that each pass when *either* header matches. A caller holding **both** `proxy.apiKey` and `byok.apiKey` can therefore put one in each header and clear both gates from the network. The surface is not reachable with the BYOK key alone, but it is not sealed off either. Serving (or hardening) BYOK remotely means making the supervisor BYOK-aware; that is a separate change. The upstream README copy's BYOK section (`docs/reference/upstream-README.md`) states this the same way. Enabling without a key logs and stays disabled, as does the `config.example.json` placeholder key, any `change-me` variant, and a key under 20 characters — the preflight answers any origin, so an unrotated default would let a page the user merely visits spend the pool (it could not read the reply, but the request would still be served). A prefix colliding with `/v1` or `/teamclaude` is refused at config load.
- **Nothing but plain API paths.** The control plane (`/teamclaude/*`), the OAuth relay (`/v1/oauth/token`, handled before body normalization and therefore not header-scrubbed), and any dot-segment path (raw or percent-encoded) are 404 on this surface. `matchByokSurface` collapses duplicate slashes first, so those checks are exact-match on a canonical string rather than safe only because unrelated downstream code happens to compare exactly.
- **Lane isolation.** A BYOK request is never staged as the warm-up probe template (a synthesized third-party shape must not become the fleet's probe), and a BYOK 429 never advances the process-global cooldown — that variable is shared with every Claude Code session, so one client's headerless 429 would otherwise stall the fleet for up to `continuityMaxSleepMs`.
- **Admission control.** BYOK shares the account pool, which has no per-client reservation, so it is rejected with 429 while `usableCount < byok.minUsableAccounts` and capped at `byok.maxConcurrent` concurrent requests. Claude Code is never rejected by these gates. Counters (`inflight`/`admitted`/`rejected`/`injected`) ride along on `/teamclaude/status` under `byok`.
- Absent config → no BYOK code path executes. Tests: `test/byok.test.js`, `test/server-byok.test.js`.

### Quota tracking (account-manager.js)

Two header families drive rotation, normalized into one model:
- **Unified** (`anthropic-ratelimit-unified-5h/7d-utilization` + `-reset`) — Claude Max/Pro. Utilization is already `0–1`.
- **Standard** (`anthropic-ratelimit-tokens/requests-*`) — API-key accounts; utilization is derived as `1 - remaining/limit`.

**Model-scoped weekly windows** (`anthropic-ratelimit-unified-7d_<label>-*`, currently `7d_oi` — the separate top-tier weekly limit shown as "Fable" in Claude's usage UI) are parsed into `quota.modelWeekly` and surfaced in the TUI (third `Fbl` bar on wide terminals) and `teamclaude status`. They are deliberately **not** used to pre-block account selection or persisted across restarts: a cached 100% value must not block the Fable/Mythos request that can refresh it. Instead, `modelQuotaLabel(model)` and `isModelExhausted()` classify the current response's live model-quota 429, then fail over or follow the configured model fallback chain without globally throttling an account that can still serve Opus/Sonnet/Haiku. These headers only appear on responses to requests *for that model tier*, so the warm-up probe template performs a one-way **upgrade** to a shape whose own response carried a `7d_*` window (see Active warm-up below). The template itself is persisted across restarts as a provisional known-good shape; the first freshly accepted request replaces it.

**Accounts with no 5-hour window (Ultra, 2026-10-30)**: verified Ultra (ex-Max 20x) subscriptions receive the 7d headers but no `anthropic-ratelimit-unified-5h-*` headers. `updateQuota(account, headers, { status })` records this as `quota.sessionWindowStated` (true when any 5h header is present; false only on a <400, non-`rejected` OAuth response carrying 7d but no 5h header; otherwise unchanged; persisted in the quota snapshot). The flag feeds only `_fullyMeasured` (so active warm-up stops re-probing the account), the cleanup of a leftover 5h reading, and display (CLI `no 5h limit`, TUI `none`, Claude status line / footer `Ses none` with the FLEET session average over accounts that have the window, app JSON `fiveHourWindow`). The OAuth usage report (`refreshAnthropicUsage`) feeds the same rule: `five_hour: null` with a valid `seven_day` counts as an accepted weekly-only response; a `five_hour` object with no reset yet (an idle window) leaves the flag unchanged. Only `provider: 'anthropic'` accounts carry the flag (grok/cursor/codex reuse `unified5h` for their own meters). Selection still gates on measured values, never on the flag.

**Usage endpoint backoff (2026-10-31)**: `/api/oauth/usage` is rate limited per token and the same tokens are shared by several machines, so `refreshAnthropicUsage` keeps a per-account, memory-only `_anthropicUsageBackoff`: 429 waits `Retry-After` (seconds or HTTP date; 5 min if absent/invalid, capped at 1 h), 403 waits 1 h, both plus 0–60 s jitter; a success clears it. Forced refreshes (TUI `R`, `teamclaude reload`) respect it too — the call returns false and `warmupAccount` falls through to the message probe, which still measures 5h/7d. One log line per failure streak (or status change), not one per cycle. A 403 `permission_error` with `oauth_scope_insufficient` (or `required_scopes` containing `user:profile`) — what long-lived setup tokens get — instead disables the call for that credential (a sha256 fingerprint kept in memory, never the token) until it changes (re-login/swap), logged once; other 403s keep the 1 h backoff.

**Fable top-up model swap (2026-10-31)**: when the committed probe template does not elicit the `7d_oi` window (no Fable traffic through the pool), `topUpModelWeekly` replays the same template with only the model swapped to `modelWeeklyProbeModel` (config default `claude-fable-5-1` — the one place a model name appears, as an overridable default; `''`/`false` turns it off). Same `_mwProbes < maxWarmupTries` budget: it stops once `modelWeekly` fills and runs again after the weekly window is swept; a 4xx (e.g. 400 unknown model) spends the whole budget instead of retrying. Real Fable traffic still upgrades the template via `commitProbeTemplate`, after which no swap is used.

`switchThreshold` (default `0.98`) is the cutoff above which an account is treated as full and skipped. Expired quota windows (including model-scoped ones) are lazily cleared inside `_isNearQuota`.

### Account selection (`getActiveAccount` in account-manager.js)

**Cold-start warm-up first**: quota is only populated after a request flows through an account (`updateQuota`), so `_nextWarmup` round-robins across the still-**unmeasured** available accounts (`_isWarmupTarget`) and `getActiveAccount` routes to them before any priority decision. Warm-up keys on `_isMeasured` (has the account ever returned rate-limit headers?), **not** on "has it made a request" — a response with no rate-limit headers (a `HEAD /`, a 404, an auth failure) must not permanently mark an account measured, or it gets trapped as unmeasured forever (sorted last by use-or-lose, bounced by the rebalance below), never used and never refreshed. `maxWarmupTries` provides the loop-safety: a genuinely dead account (always header-less / 401) is abandoned after a few attempts. An expired-token account resolves on its first warm-up routing — `ensureTokenFresh` refreshes it into a measurable state or marks it `error`. Only once no unmeasured account remains does priority selection run.

Selection is then **use-or-lose**, not round-robin: among accounts under the threshold, `_selectBest` picks the one whose **weekly (7d) quota resets soonest** (`_weeklyResetTime`) — the weekly window is the scarce resource, so an account whose week is about to renew (and whose unspent quota would be wasted) is drained first — tie-broken by **soonest session reset** (`_sessionResetTime`), then **lowest session utilization** (`_sessionUtilization`). Accounts with no weekly data (API-key, or an expired/unmeasured 7d window) rank at `Infinity` and tie, so the session tiebreak reproduces the pre-weekly ordering for them. **Reset rollovers reflect immediately**: a timestamp that has passed also ranks at `Infinity` (`_weeklyResetTime`/`_sessionResetTime` clamp) — otherwise the past timestamp (smallest value) would pin the account at the top of the auto order until a request-path sweep cleared it. The warm-up timer additionally calls `sweepExpired()` every interval so an idle proxy clears rolled-over windows (→ unmeasured → re-probed → fresh order) without needing traffic. The session/utilization helpers fall back from unified (Max) to standard (API-key) metrics.

**Manual controls layered on top (don't change the use-or-lose core when unused):**
- **Disable / enable** (`setEnabled`, config `enabled: false`): a disabled account is excluded from rotation by a single gate in `_isAvailable` (which every selection path — warm-up, `_selectBest`, `_cappedSet`, `anyUsable/anyCapped`, the sticky-current check — already funnels through; `_recoverSoonest` skips disabled accounts itself). In-flight requests on a just-disabled account **drain** (the flag doesn't touch `inflight`); re-enabling calls `_drainWaiters()` so its freed capacity is handed to any queued waiter immediately. Surfaced as `status` "disabled" in the TUI (the default view has a **`↑/↓`** selection cursor; **`e`** toggles the selected account directly) and `[disabled]` in `teamclaude status`; CLI `teamclaude disable|enable <name>`.
- **Explicit priority / order** (`setPriority`, config `priority: <int>`): `_selectBest` sorts by `_priority` **first** (lower number = preferred), then the existing reset/util use-or-lose as tiebreakers. Unset is `null` → `_priority` returns `Infinity`, so **when no account sets a priority every account ties there and the sort falls through to the original use-or-lose unchanged**. In the TUI this is surfaced as an **order**, not a number: the default view has a **`↑/↓`** selection cursor (the action keys — `s` switch, `e` enable/disable, `o` order — act directly on the selected account; only the destructive `d` keeps a confirmation step), and **`o`** grabs the selected account into a move mode where **`↑/↓` reorder** it, **`a` resets the WHOLE order** (clears every rank — the fleet returns to auto weekly-reset ordering), and **`c` clears just the grabbed account's rank** (`_keyNormal` / `_moveOrder` / `_setAutoOrder` / `_applyRanking` in tui.js). Ranked accounts get contiguous priorities `0,1,2,…` and render as `#1 #2 …` (most-preferred first, shown above the rest); moving an unranked account up ranks it at the bottom of the ranked group, moving the last ranked account down un-ranks it back to use-or-lose — so you pin a few accounts and the rest stay on the auto rotation (weekly reset soonest first). The TUI list is sorted by this order (`_displayList`: ranked first, then unranked in their actual auto drain order via `autoCompare` — weekly reset soonest first; ties keep array order since the comparator returns 0 and the sort is stable). A move renumbers to contiguous values, normalizing any legacy/duplicate priority numbers. CLI `teamclaude priority <name> <n|auto|clear>` still accepts raw numbers.
- **Prompt re-pick on change** (`_reprioritize`, called by both setters): a preference change re-picks the active account *directly* and at once — but only when it actually matters, i.e. the current account is no longer usable, or another account is **strictly preferred** by the full order (`_strictlyPrefer`: priority → soonest reset → least used). A no-op (or a change that doesn't dethrone the current) leaves the sticky primary untouched, so it can't churn cache locality, and it does **not** poke `lastEvalAt` (which would wake the periodic tie round-robin). This makes a change take effect immediately even with the re-eval timer off (`reevalIntervalMs <= 0`), and lets clearing a priority restore use-or-lose routing.
- **Interaction with connection affinity (intended):** `_reprioritize` moves the *global* sticky primary, but a live keep-alive connection with an established `_affinity` home keeps routing to that home (cache locality) — exactly as it already does for the periodic `reevalIntervalMs` re-prioritization. So an explicit **priority** change routes **new** connections by the new order immediately, while existing keep-alive connections follow it once their socket closes (or their account caps). **Disable** is different: it's a hard exclusion, and the affinity path requires an *available* home (`_isAvailable`), so a disabled account drops its keep-alive connections on their next acquire too. Set `config.sessionAffinity: false` to route every request purely by priority/use-or-lose with no connection pinning.
- Both fields persist in `config.accounts[]` (survive token-refresh writes and `saveConfig`), and `syncAccountsFromDisk` applies disk changes to the live `AccountManager` on reload (TUI **R** / restart) so a CLI `disable`/`priority` while the server runs takes effect without an edit race.

To balance this against Anthropic's per-account prompt cache (separate per org → switching mid-stream causes cache-miss cost), the active account is **sticky**: priority is only re-evaluated once per `reevalIntervalMs` (default 5 min, `config.reevalIntervalMs`), plus immediately whenever the current account becomes unavailable (over threshold / throttled / error). `lastEvalAt = 0` forces a priority pick on the first request. When all accounts are over threshold, `_recoverSoonest` returns the soonest-to-reset (and `getActiveAccount` returns `null` until then, yielding a `429`).

### Active warm-up (server.js) — populate the whole fleet after a restart

The cold-start warm-up above is **passive**: it only measures an account when a *client* request happens to route there, so on a fresh (re)start the dashboard shows most accounts as "—" until traffic organically reaches each one — Anthropic has **no "get my quota" endpoint**, so quota is only ever learned from real `/v1/messages` rate-limit response headers. **Active warm-up** (`createProxyServer`, gated by `config.activeWarmup` — default on) closes that gap by proactively probing the unmeasured accounts:

- **Capture-and-replay template.** The first genuine `POST /v1/messages` that passes through is snapshotted into `probeTemplate = { model, version, beta, system }` (path-exact, so `/v1/messages/count_tokens` isn't mistaken for inference). Replaying a *known-accepted* shape — the exact model, `anthropic-version`/`anthropic-beta`, and the Claude-Code `system` prompt an OAuth request requires — means a probe can't fail with a guessed-wrong 4xx, and never needs hardcoded model/beta strings that drift. Staging/committing happens **after** the response (the body parse is only paid when a commit is possible), and exactly one one-way **upgrade** is allowed: a shape whose own response carried a model-scoped `7d_*` window (`_elicitsModelWeekly`, tracked via `ctx.sawModelWeekly`) replaces a committed shape that didn't — otherwise probes replaying a lower-tier template could never refresh the Fable weekly numbers. No downgrade: later lower-tier traffic leaves the upgraded template in place.
- **Minimal probe.** Background `warmupAccount` skips an OAuth account whose token is expiring soon, then sends a `max_tokens: 1` `/v1/messages` with the account's own auth header (`Bearer` for OAuth, `x-api-key` otherwise), folds accepted response `anthropic-ratelimit-*` headers into `updateQuota`, and cancels the body. The explicit TUI **R** path refreshes eligible OAuth tokens before forcing re-measurement. Warm-up is **best-effort**: any failure leaves the account unmeasured exactly as before, so client traffic is never affected. Probes run **outside** concurrency-cap accounting and only target eligible idle accounts.
- **When it runs.** When a template is first captured, `setImmediate(warmupUnmeasured)` fans out to every unmeasured account in parallel. On later restarts the last accepted template is restored from the quota snapshot, so TUI **R** and periodic probes can work before fresh traffic arrives. Then periodically every `config.warmupIntervalMs` (default 5 min; `0` = startup-only) the timer also re-populates accounts whose quota window just **reset**. `warmupInFlight` prevents overlapping fan-outs; a per-account `_warming` flag prevents duplicate concurrent probes. The interval is `unref`'d and cleared on `server.close()`.
- **First-run limitation:** on a brand-new proxy with no snapshot and zero traffic there is no known-accepted template yet, so nothing is probed until the first real request flows. `config.activeWarmup: false` disables capture, restore, fan-out, and the periodic timer entirely.
- **Forced fleet re-measure (TUI `R`)**: the plain warm-up only probes accounts that aren't fully measured, so displayed usage drifts silently when quota is spent *outside* this proxy (another device/session). `server.refreshQuotaAll()` (wired to the TUI Reload path after the config sync) probes EVERY idle account — measured, throttled or near-quota included (their exhausted-429 responses still carry authoritative headers), **and disabled accounts too** (out of *rotation*, not *monitoring* — a probe is read-only so it refreshes their dashboard row without re-enabling them) — skipping only in-flight (`inflight > 0`) and auth-error accounts, and renews the convergence budgets first. Returns `{ targets, measured }`, or `-1` when no template has been committed yet (surfaced honestly in the activity log instead of a silent no-op). Deliberately not exposed over HTTP — it spends real upstream requests.
- **Model-weekly (Fable) top-up (`topUpModelWeekly`)**: the `7d_oi` window only appears on Fable-tier responses, so an account measured for 5h/7d by lower-tier traffic keeps a blank `Fbl` bar — and because it's *fully measured*, ordinary warm-up never re-probes it. The periodic timer runs a bounded top-up pass (only once the committed template `_elicitsModelWeekly`) over accounts flagged by `needsModelWeekly` (fully measured, `modelWeekly` empty, under the `_mwProbes` cap), so the Fable numbers self-heal within a warm-up interval; an on-demand `R` heals them immediately. The cap (reset when the window populates or a quota window is swept) stops an account whose upstream genuinely never reports the window from being probed every interval forever.

### Concurrency (per-account cap + overflow queue)

`getActiveAccount` alone funnels every concurrent terminal onto the one sticky account, which then hits Anthropic's per-account rate/concurrency limit (429) while other accounts sit idle. `acquireAccount()`/`releaseAccount()` layer **proactive load spreading** on top **without changing `getActiveAccount`** (so its warm-up / use-or-lose / recover behavior — and the tests that pin it — are untouched):

- Each account has `inflight` (in-flight count) and `maxConcurrent` (cap; `config.maxConcurrentPerAccount` default 3, per-account `maxConcurrent` override). `_tryAcquire` folds **capped** accounts into the exclude set and reuses `getActiveAccount(exclude)` to pick the best account *with a free slot* — filling A to its cap, then B, then C, by use-or-lose priority. JS is single-threaded so select→`inflight++` is race-free.
- When every available account is at its cap, `acquireAccount` **queues** the request (FIFO `_waiters`) up to `config.overflowQueueTimeoutMs` (default 15s); a `releaseAccount` drains waiters. Timeout → `null` → the client gets a `429`. If instead *no account is available at all* (quota-exhausted, not merely capped) it returns `null` immediately (no pointless wait). A queued request is **cancelled if the client disconnects** (an `AbortController` tied to `res` 'close' → `acquireAccount`'s `signal`) so it can't acquire a slot later and burn upstream quota for a response nobody is waiting for.
- **Memory bounds (localhost auth is skipped, so any local process could flood):** `server.js` enforces a global admission cap covering **every body-buffering path** (the proxied path *and* the `/v1/oauth/token` relay) — `inFlightProxied` may not exceed `accountManager.totalCapacity()` (sum of per-account caps + `overflowQueueMaxDepth`, default 256) — and **rejects with `429` before buffering** the body. Per-request body size is capped by `config.maxRequestBytes` (default 32 MiB → `413`, enforced on the proxied path and inside `relayRaw`). Together they bound total buffered memory at roughly `totalCapacity × maxRequestBytes`.
- `forwardRequest` reserves a slot per attempt and releases it on completion (request `finally`) or before a failover recursion (`releaseHeld()`); a 401 same-account refresh-retry keeps the slot. Status/TUI expose `inflight`/`maxConcurrent`.
- **Connection affinity (prompt-cache locality):** `acquireAccount(..., affinityKey)` takes the client **socket** (`req.socket`) as a soft key. The first acquire on a connection remembers its account in a `WeakMap` (`_affinity`, value is the account *object* + an `accounts[i] === a` identity guard against a `removeAccount` re-index; GC'd when the socket closes); subsequent acquires on the same connection **prefer that account**. It's *soft* — honored only if that account is still available, has a free slot, and isn't `exclude`d, else it falls through to normal `_tryAcquire`. So HTTP/1.1 keep-alive (a session's **sequential** turns reuse one socket) keeps a terminal on one account (cache warm), while a **concurrent** burst — which necessarily opens separate sockets — still spreads by the cap logic. It never exceeds a cap or revives an exhausted account, so the 429 guarantees and use-or-lose for *new* connections are unchanged. It also **defers to cold-start warm-up** (skipped while any account is still a warm-up target) so it can't pin all of one connection's traffic to a single account and starve the others of quota data; only object/function keys are honored (a primitive key is ignored, never a `WeakMap` throw). Crucially this also blunts the periodic `reevalIntervalMs` re-prioritization: when the global sticky primary moves, live connections keep their own account (no mass cache-bust); only new connections follow the new primary. **Caveat:** the key is the TCP socket, so "session" = connection. The normal case (one Claude Code process per terminal → its own connection) maps 1:1, but an intermediary that multiplexes *unrelated* logical sessions onto one keep-alive socket (e.g. a pooling agent with `maxSockets: 1`) would make them share an affinity and defer use-or-lose rotation until that account caps/exhausts — set `config.sessionAffinity: false` for such a front-end. Disabling routes purely by use-or-lose every request.

### Concurrency semantics & limits (what the cap is and isn't)

- The cap is on **concurrent in-flight requests per account, not "terminals."** A terminal is usually idle (waiting on the user / model), so it holds a slot only mid-request. `maxConcurrent: 3` means "≤3 requests upstream *at once* on this account," which is the right unit for burst rate-limiting — not a hard binding of 3 terminals to an account.
- **Spreading only kicks in on overflow.** While concurrent in-flight ≤ cap, traffic concentrates on the sticky primary (good for cache); other accounts stay idle until the primary is capped, then fill by use-or-lose. To spread *eagerly* across accounts, lower `maxConcurrentPerAccount` (e.g. `1`) at the cost of intra-account cache sharing.
- **The cap stops *burst / request-rate* 429s, not *quota-exhaustion* 429s.** A single large request can still exhaust an account's 5h/7d token quota with one slot in use; that path is handled separately (`isExhausted` → throttle the account + switch, in `forwardRequest`). Two complementary mechanisms — the cap is not a blanket 429 cure.
- **Caps are per-process.** Running two proxy instances against the same accounts does not share `inflight`, so combined concurrency can exceed the per-account intent. Single-proxy is the design assumption.

### Quota persistence across restarts (`<config>.quota.json`)

Quota lives only in memory, so a restart used to blank the whole dashboard (and blind use-or-lose ordering) until traffic organically re-measured every account. The server now snapshots per-account quota/throttle/usage state plus the active-account name (`exportQuotaState` in account-manager.js) to `<config>.quota.json` — written every minute (unref'd interval) and synchronously in a process `'exit'` handler (covers TUI quit and SIGINT/SIGTERM; a SIGKILL loses at most the last minute) — and restores it at startup (`importQuotaState`, wired in `serverCommand`). Restores are stale-safe: the proxy takes no traffic while down, expired windows are lazily swept by `_isNearQuota`, a `rateLimitedUntil` in the past is not re-applied, and `error`/`exhausted` statuses are deliberately never persisted (a bad token may have been fixed since). Restored accounts count as measured, so warm-up doesn't re-probe them. Matching is by `accountUuid` then `name`, same as config sync.

### Server lifecycle (status / stop / restart)

The supervisor writes a **state file** next to the config (`getServerStatePath()` → `<config>.server.json`: `{ pid, workerPid, port, startedAt }`) after its worker is ready and removes it on exit. The public listener belongs to `pid`; a non-zero worker crash replaces `workerPid` while the listener and queued requests survive. A supervisor SIGKILL can leave a stale file, which the next command detects and cleans up. `findRunningServer` probes candidate ports — the **state file's recorded port first** (it may differ from the current config port after an edit, and probing only the config port would miss → orphan the live server), then the config port — and accepts a port only if it answers a TeamClaude-shaped `/teamclaude/status` (a foreign process is *not* mistaken for ours → falls through to the EADDRINUSE message). The owning pid is resolved authoritatively via `lsof` (never a possibly-recycled state-file pid); the state-file pid is only a fallback when `lsof` is unavailable. `stop`/`restart` signal the supervisor, which drains or force-stops its worker, and `server` refuses to start a duplicate on an occupied port.

## The thing that's actually hard: config ⇄ memory synchronization

Most of the commit history is token-rotation/sync bug fixes. There are **three concurrent writers** to the config file:
1. The running server persisting refreshed OAuth tokens (`onTokenRefresh` callback in `index.js`).
2. The TUI's `saveConfig` (after import/add/remove).
3. External `teamclaude import`/`login`/`reauth` run while the server is up (picked up via TUI **R**, SIGHUP reload, or `syncAccountsFromDisk`).

Rules every config write must follow (see `atomicConfigUpdate`, `findConfigAccount`, `syncAccountsFromDisk`):
- **Always re-read disk before writing.** `atomicConfigUpdate(updater)` does this; never blind-`saveConfig` from a long-lived in-memory copy, or you clobber accounts added by another process.
- **Match accounts by `accountUuid` first, then by `name`.** Indexes shift; this matching is the dedup/sync key used everywhere.
- **Never overwrite fresher tokens with staler ones.** `syncAccountsFromDisk` compares `expiresAt` (`diskIsStaler`) before applying disk credentials over in-memory ones.
- **Never reload across a pending account quarantine write.** The structured
  organization-access 403 path awaits `onAccountFlag`; SIGHUP/TUI reads use
  `readAfterAccountFlagWrites` so stale disk state cannot re-enable that account.
- Treat `AccountManager.accounts[i].credential/refreshToken/expiresAt` as the authoritative *live* tokens; the `config.accounts` array can lag.

Related gotcha: **`expiresAt` may arrive in seconds or milliseconds.** OAuth endpoints return seconds; Claude Code credentials use milliseconds. Always pass through `normalizeExpiresAt` (oauth.js) — assuming one unit was a recurring bug.

## Other intentional behaviors

- **Model fallback (`config.modelFallbacks`, qjc fork)** — when the WHOLE fleet is out of quota for the requested model (model-tier exhaustion, selection-time dead end, or an unlabeled fleet-wide 429), `forwardRequest` rewrites the request body's `model` to the next entry of the configured chain (e.g. `{"claude-fable-5": ["claude-opus-4-8", "claude-sonnet-5"]}`) and retries the fleet with reset tried-sets, instead of surfacing the 429. The chain is resolved once per request from the ORIGINAL model (no fallbacks-of-fallbacks), req.headers' `content-length` is kept in sync with the rewritten body (it is forwarded, not hop-by-hop), and when the chain runs dry the pre-existing 429/continuity behavior applies unchanged. Config keys/targets must be plain API model IDs — a bracket-suffixed incoming model (`claude-fable-5[1m]`, a client-side notation the API rejects as `not_found_error`) matches its suffix-stripped entry. Fallback runs BEFORE a continuity-mode sleep on purpose: rewriting to a served model beats sleeping until a weekly reset. Tests: `test/server-model-fallback.test.js`.
- **`run` deliberately sets only `ANTHROPIC_BASE_URL`, not `ANTHROPIC_API_KEY`** — this keeps Claude Code in subscription mode (full model access) while routing through the proxy, which accepts the client's own OAuth token from localhost.
- **Account dedup** happens in `accounts` command and on every upsert: by `accountUuid`, keeping the most recently added.
- Token refresh is **coalesced** via `account._refreshPromise` so concurrent requests trigger one refresh.
- **Token keep-alive sweep** (`refreshLapsedTokens` in account-manager.js, wired on a timer in `serverCommand` — `config.tokenRefreshIntervalMs`, default 5 min, `0` = off, plus one immediate sweep at startup): periodically refreshes OAuth accounts whose access token is expiring/expired, **sequentially** (a fleet-wide lapse after downtime must not burst N concurrent POSTs at the token endpoint; overlapping sweeps are skipped via `_sweepInFlight`). Rationale: warm-up probes deliberately never refresh tokens and client traffic concentrates on the sticky account, so an idle account's refresh-token chain stops rotating and can be invalidated upstream. Parked (`error`) and disabled accounts are swept too — their chains must survive to be usable when they heal. **Error healing is cause-scoped** (`_errorFromRefresh`): a refresh-caused error (set by `ensureTokenFresh`'s catch) clears `error` → `active` on the next successful refresh — the thing that failed now succeeded; an error set by the *request path* (upstream 401 despite a fresh token at server.js's 401 handler, or a non-transient send failure) is **not** revived by a token-endpoint success (that would flap a rejected account back into rotation every sweep) — those heal only via `updateAccountTokens` (re-import/login) or a restart. The cause tag is set only on the error *transition*, so a later failed sweep refresh can't relabel an upstream-auth error as refresh-caused. Because a request-path 401 park is this sticky, the 401 handler will not create one on evidence that points at the request rather than the account — see the cascade guard in Request flow 6.5.
- Streaming responses must check `res.destroyed` to stop pulling from upstream when the client disconnects, and handle backpressure by racing `drain` against `close`.
- Log lines are prefixed `[TeamClaude]`; the TUI strips that prefix when mirroring `console.log`/`console.error` into its activity pane. Credentials are masked (sliced) in `--log-to` request dumps.
